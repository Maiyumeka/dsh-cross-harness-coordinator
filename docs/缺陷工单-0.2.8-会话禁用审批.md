## 一句话结论

**在"DSH 侧完全权限 + 会话禁用审批提示"的组合下，Codex 端任何需要审批的操作都会被 DSH 原生审批层自动拒绝；插件、Codex、环境均无故障，但任务会在执行中途必然失败，且插件未在派发前告知这一点。**

**因此审批请求注定被拒 —— 不是"这次命令太危险"，而是"本会话没有任何人/任何通道能批准"。**

## 三、请修的三点

### 3.1 派发前应能预判"本会话无法批准"

当前行为：任务已 queued → 已 started → 模型已生成图片（**已花费额度与时间**）→ 走到命令执行才申请审批 → 被拒 → 失败。

期望行为：**在 `coordinator_plan` 接受任务时（或 `pump()` 派发前）就检测该端点是否需要操作审批、以及原会话是否具备批准能力**。若不具备，应当：

- 要么在计划阶段就明确报错/警告（例如「Codex 端在本会话需要操作审批，但当前会话禁用审批提示，本任务预计无法完成」）；
- 要么在任务记录里带上一个显式标记，让当前 Agent 在派发前就能改道（改派其他执行端 / 调整任务形态）。

**本次代价**：连续 4 次派发、4 张图生成、约 20 分钟，全部因同一个结构性原因失败。

### 3.2 应提供"无需审批即可回收产物"的通道

这是本次最实际的痛点。Codex 的 imagegen 技能明确规定：

> Built-in save-path policy: Codex saves generated images under `$CODEX_HOME/*` by default.
> **Never leave a project-referenced asset only at the default `$CODEX_HOME/*` path.**
> For project-bound work, **move or copy** the selected artifact into the workspace.

即 **"生成 → 搬入工作区"是 imagegen 的正常流程**，而搬移必然触发 `item/commandExecution/requestApproval`。在当前会话形态下，这个正常流程 100% 失败。

**建议**：让 Codex 端的产物可从 `$CODEX_HOME/generated_images/<threadId>/` 直接回收，而不必依赖执行端自己执行命令。可行的方向：

- 插件在 `native.js` 完成 `turn` 后，把 `generatedImages[].savedPath` 作为**已生成产物**记录进 `result`（现在只记录在 `native.generatedImages` 里，未进入 `artifacts`，也没有被搬进工作区的机制）；
- 或提供一个显式的"产物回收"动作，由发起方（当前 Agent，拥有完全文件权限）把指定路径的文件复制到声明的输出路径，**不经过执行端审批**。

### 3.3 失败原因应指向"审批通道不可用"，而不是"操作被拒"

当前 `error`：

```
Codex操作审批未通过：DSH审批结果：rejected
```

这在"审批被拒但渠道畅通"与"审批渠道根本不存在"两种情况下一模一样。建议区分：

- 渠道可用但人工/策略拒绝 → 「操作未获批准」
- 渠道不可用（本会话禁用审批提示）→ 「本会话无法提供操作批准，Codex 端的命令执行类操作不可用」
