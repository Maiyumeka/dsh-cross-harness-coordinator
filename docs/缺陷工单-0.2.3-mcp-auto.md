## 实测证据

### A. `era:auto` 失败（0.2.3 安装后、`reconfirm` 前）

```json
{"endpointId":"h_0c3e90b77b86","registered":true,"connected":false,
 "connection":{"protocol":"mcp","transport":"stdio","handshakeVerified":false,
   "negotiationAttempts":[
     {"era":"modern","method":"server/discover","ok":false,
      "error":"MCP连接或调用超时：server/discover"}],
   "state":"needs_agent","stage":"server/discover",
   "error":"MCP连接或调用超时：server/discover",
   "checkedAt":"2026-10-06T02:54:29.408Z"}}
```

**关键点：`negotiationAttempts` 数组只有 1 条（modern），没有 legacy 那条。**

按 `lib/mcp.js:127-135` 的写法，进入 `catch` 后**必定**会 push 一条 modern 记录；若降级成功，`line 135` 还会 push 一条 legacy 记录（无论成败）。既然数组里没有 legacy 条目，说明**代码在 `line 130` 抛出了异常，从未执行到 `line 131` 的 `reconnectLegacy()`**：

```js
// lib/mcp.js:127-135
try{discovered=await req('server/discover',{});negotiationAttempts.push({era:'modern',...,ok:true});}
catch(error){
  negotiationAttempts.push({era:'modern',method:'server/discover',ok:false,...failureDetails(error)});
  if(error.rpcError?.code===-32022){...}
  else if(e.mcp.era==='modern'||signal.aborted||fatal)throw error;   // ← line 130：在此抛出
  else{phase='legacy/reconnect';await reconnectLegacy();}            // ← line 131：未到达
}
...
if(!modern){phase='initialize';try{init=await req('initialize',{...});negotiationAttempts.push({era:'legacy',...,ok:true});}
            catch(error){negotiationAttempts.push({era:'legacy',...,ok:false,...});throw error;}}
```

**为什么 `signal.aborted` 会是 true？**

```js
// lib/mcp.js:78-79
const fail=error=>{fatal=error;rejectAll(error);void h.stop().catch(()=>{});};
const onAbort=()=>{cancelAll('用户取消或调用超时');rejectAll(...);void h.stop().catch(()=>{});};
// lib/mcp.js:81
signal.addEventListener('abort',onAbort,{once:true});
// lib/mcp.js:123
signal.throwIfAborted();timer=setTimeout(()=>{const error=Error(probeOnly?'MCP连接检查超时':'MCP任务执行超时');cancelAll(error.message);fail(error);},task.timeoutMs);
```

`fail()` 本身不 abort，但**调用方的探针 signal 若在连接检查期间超时被 abort**，`onAbort` 会 `rejectAll()`，`server/discover` 的 pending 请求被以 `signal.reason` 拒绝——该 Promise 的拒绝**没有 `rpcError`**，于是 `line 130` 命中 `signal.aborted===true` 并抛出。

### B. 计时观测（支持"两种超时互相踩"）

```
10:55:24.429  本地发出 connect
02:55:32.477Z 返回的 checkedAt（= 10:55:32.477 本地）
→ 总耗时 ≈ 8.0 秒
```

而 `server/discover` 的**请求级**超时是 `Math.min(task.timeoutMs,1500)` = **最多 1500ms**（`lib/mcp.js:118`）。

**1500ms 的请求超时与最终 ~8s 的总耗时对不上**，说明这次失败并非单纯由 `server/discover` 的请求超时决定，而是请求级超时与全局 `task.timeoutMs`（约 8s）交织；`stage` 停留在 `server/discover` 也印证了流程没能干净地进入 legacy 阶段。

## 建议的修复

1. **`server/discover` 的失败必须能降级，不管错误形态。**
   当前只认 `-32022`；`-32601`（Method not found）与**超时**都应视为"现代路径不可用"。
   最直接的判据：**只要没拿到 `resultType==='complete'` 的 discover 结果，就降级**，除非 `era` 被显式声明为 `modern`。

2. **`line 130` 的 `signal.aborted` 会让降级永远不可达。**
   探针超时（时间到了）与"用户主动取消"是两回事，但此刻都表现为 `signal.aborted===true`。
   建议区分：
   - 用户显式取消 → 抛错
   - 探针自身超时 → 仍尝试一次 legacy 降级（用剩余预算或独立短超时）

3. **请求级超时与全局超时相互踩。**
   `server/discover` 1500ms 的请求超时本应触发降级，但全局 `task.timeoutMs`（约 8s）也在推进 `fail()`/`abort`。
   建议降级尝试**不受**全局超时判据影响，或给降级阶段单独一段短预算。

4. **失败时把两条路径都记上**（0.2.3 已加了 `negotiationAttempts`，很好）。本次只有 modern 一条，正是"没走到 legacy"的证据——**这个字段已经能自证问题**，建议在 UI/工具返回里也把 `negotiationAttempts` 显示出来，排查会更快。
