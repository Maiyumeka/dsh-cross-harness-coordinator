## 失败断言（定位到行）

`test/mcp-budget.mjs:66`

```js
h=host({initialize:'silent'});hosts.push(h);
error=await failure(runMcp(h,request({task:{timeoutMs:300}})));
assert.equal(h.launches.length,2);
assert.equal(error.protocolStage,'initialize');        // ← 这条在套件里偶发失败
assert.equal(error.connectionReceipt.negotiationAttempts.length,2);
assert.equal(error.connectionReceipt.diagnostics.abortSource,'mcp_deadline');
```

失败信息（每次都是同一条）：

```
Expected values to be strictly equal:
+ actual   'cleanup'
- expected 'initialize'
```

> 已确认 `node:assert/strict` 的 `assert.equal(actual, expected)` 中**第一参数是 actual**：
> `assert.equal('FIRST_ARG','SECOND_ARG')` 的输出为 `+ 'FIRST_ARG'  - 'SECOND_ARG'`。
> 因此上表含义是"**实际得到 `'cleanup'`，期望 `'initialize'`**"。

场景说明：mock 对 `initialize` **永不回应**（`initialize:'silent'`），预算 300ms。测试意图是"已进入 legacy 但握手卡住时，保留双路径错误与总超时来源"，即期望阶段为 `initialize`。

## 竞态分析

该场景下两条超时路径**几乎同时**触发，先到者决定最终 `protocolStage`：

### 路径 A：`initialize` 请求级超时 → 报 `initialize`

```js
// lib/mcp.js:144
if(!modern){phase='initialize';try{init=await req('initialize',{...});...}}
```

`req()` 对非 `server/discover` 方法的超时是 `Math.min(task.timeoutMs,15000)` = **300ms**：

```js
// lib/mcp.js:128
const requestTimer=setTimeout(()=>{pending.delete(id);...
  reject(timeoutError('MCP连接或调用超时：'+method,'MCP_REQUEST_TIMEOUT',timeout));},timeout);
```

→ 抛出时 `phase==='initialize'`，`annotate()` 记为 `initialize`（这就是期望值）。

### 路径 B：总预算耗尽 → 报 `cleanup`

```js
// lib/mcp.js:132   全局预算定时器
timer=setTimeout(()=>{const error=timeoutError(probeOnly?'MCP连接检查超时':'MCP任务执行超时','MCP_DEADLINE',diagnostics.totalBudgetMs);...},task.timeoutMs);

// lib/mcp.js:124   任何请求发起前先检查预算
const budget=remaining();if(!budget){reject(timeoutError('MCP连接或任务总预算已耗尽','MCP_DEADLINE',diagnostics.totalBudgetMs));return;}

// lib/mcp.js:182   清理结束时预算已尽
if(!remaining()){const error=timeoutError('MCP清理结束时总预算已耗尽','MCP_DEADLINE',diagnostics.totalBudgetMs);error.protocolStage='cleanup';throw annotate(error);}
```

→ 若"总预算已耗尽"的判断先于请求级超时被观察，错误就会被贴成 `cleanup`。

**两条路径的时限都等于 `task.timeoutMs`（300ms）** —— 这是竞态的根本原因：它们不是"谁先达到条件"，而是"同一个 300ms 边界上谁先被调度执行"，受进程负载、事件循环排队顺序影响。套件里前面 6 个测试都启动过真实子进程，负载与单独运行时不同，于是偶发踩到另一条路径。

同类窄窗口在 `mcp-budget.mjs` 里还有多处：

```
line 56-57   budget 250ms / cleanupDelay 400ms   （断言 protocolStage='legacy/reconnect'）
line 60      budget 250ms / cleanupDelay 400ms   （断言 protocolStage='cleanup'）
line 66      budget 300ms / initialize 静默       （断言 protocolStage='initialize'）
line 70-71   deadlineAt=begin+650 / versionDelay 350（断言 totalBudgetMs<350、总耗时<1000ms）
line 74      deadlineAt=Date.now()+150            （断言 protocolStage='connection_budget'）
```

这些断言都建立在"毫秒级顺序可预测"的假设上。

## 建议的修复

### 一、测试侧：消除毫秒级竞态（必要）

优先用**可控时钟**而不是真实毫秒：

1. **把 `task.timeoutMs` 的竞争点错开**：让请求级超时与总预算之间留出明确余量（例如预算 800ms、mock 300ms 不回应，断言 `initialize`），而不是让两者都等于 300ms。
2. **或改用假定时器**：注入可推进的时钟，显式"推进到 X ms"再观察状态，彻底摆脱调度抖动。
3. **或把断言改为由【原因】判断，而非由【时间】判断**：

```js
// 现在的写法（脆弱）：阶段由谁先到决定
assert.equal(error.protocolStage, 'initialize');

// 建议的写法（稳定）：先断言原因，再由原因推导阶段
const d = error.connectionReceipt.diagnostics;
assert.equal(d.abortSource, 'mcp_deadline');            // 已经是确定性证据
assert.ok(['initialize','cleanup'].includes(error.protocolStage));  // 阶段作为"观察到的事实"
assert.ok(d.cleanupMs >= 0 && d.failedPhase === error.protocolStage);
```

   若确实要断言"必须是 initialize"，就应通过**拉大预算余量**让路径 B 不可能先发生。

4. **对 `line 74`（deadlineAt=+150）这类极窄窗口**，建议同样拉宽或改为断言"进入了 connection_budget 分支"这一**布尔事实**，而不是紧凑的毫秒边界。

### 二、实现侧：让"阶段归属"成为确定量（更好）

0.2.4 已经加了 `diagnostics.abortSource` / `failureDetails.kind` / `fallbackDecision`，方向完全正确。建议再走一步：**让阶段由失败原因唯一决定**，而不是由时间先后决定。

例如约定：

```
kind='request_timeout' 且失败的 method='initialize'  → protocolStage 必为 'initialize'
kind='mcp_deadline' 且已经过了握手阶段                → protocolStage 必为 'cleanup'
```

即：`protocolStage` 应当可以从 `(failedMethod, kind, phase)` **纯函数式推导**，不依赖"哪条超时先被观察"。这样外部（UI / 工具返回 / 测试）就能稳定判读。

### 三、跑测方式：隔离（可选，但值得）

`test/run.mjs` 当前同进程 `import()` 顺序加载。若希望彻底消除跨文件影响：

- 每个测试文件用**子进程**跑（`node test/xxx.mjs`），失败可独立归因；
- 代价是启动开销增加（当前整套约 45 秒）。

即使做了隔离，**上面的竞态仍存在**（单独跑只是恰好稳定），所以一、二两步不能省。
