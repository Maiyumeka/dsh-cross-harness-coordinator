### 为什么这是缺陷（关键）

**没有任何一条合法路径能让用户"重新确认"这个执行端。** 可用的出口只有两个，都不通：

```
① coordinator_control action=connect（提示让 Agent 用这个）
   → 只做校验，不做重新基线；definition 参数也不含 fingerprints
     （connectEndpoint(actor,id,{signal,definition})，definition 只覆盖调用定义字段）

② 重新登记同一 id
   → lib/engine.js:88:  e.fingerprints=this.fingerprints(e);this.state.endpoints[e.id]=e;
     【无条件覆盖】── 见缺陷 2
   → 而 lib/onboarding.js:23 又有守卫：
     if(Object.values(sessions).some(s=>s.tasks.some(t=>t.endpoint===id &&
        !['cancelled','failed','unverified'].includes(t.status))))
       throw Error('已有任务引用该执行端，不能通过邀请修改调用定义');
   → 本机该执行端有 3 个 passed 任务引用 → 重登记被拒
```

**净结果：执行端永久卡在 `needs_agent`，且提示的修复动作（connect）不可能成功。** 这正是本次这个执行端的现状。

### 期望的修复（建议）

1. **提供一条明确的"重新确认接入"路径**，至少做到：
   - 重算指纹 → **逐项列出差异**（文件、旧哈希、新哈希、文件 mtime）→ 由用户/Agent 明确确认 → 才更新基线；
   - **不能静默覆盖**（见缺陷 2）。
2. **`coordinator_control` 增加该动作**（例如 `action=reconfirm`，或让 `connect` 在指纹不符时返回"可确认的差异清单"而不是直接抛错），使提示里的"请重新确认接入"真的有对应动作。
3. **`stage` 字段要如实反映失败阶段**：现在是 `launch`（因为 `checkEndpoint` 抛的是不带 `protocolStage`/`acpStage` 的普通 `Error`，被 `error.protocolStage||error.acpStage||'launch'` 兜底成了 `launch`），实际是**指纹校验**阶段。见 `lib/engine.js:123`：
   ```js
   e.connection={...stripUndefined(error.connectionReceipt||{}),state:'needs_agent',
     stage:error.protocolStage||error.acpStage||'launch',error:String(error.message||error).slice(0,2000),...};
   ```
4. **登记时就该自洽**：`version` / `reported` 里声称的版本，应当来自与命令行**同一个**入口文件的实跑结果；否则记录的指纹与命令行必然对不上。

## 缺陷 2 ★★ 指纹基线可被静默覆盖（信任根可被重置）

```js
// lib/engine.js:88  register()
requireValue(!this.state.endpoints[e.id]||this.state.endpoints[e.id].owner===s.id,'执行端属于其他会话');
e.fingerprints=this.fingerprints(e);     // ← 直接用"现在这份文件"的哈希覆盖旧指纹
this.state.endpoints[e.id]=e;
this.event(s,'endpoint','用户接入邀请登记 '+e.label);
```

**问题**：`e.fingerprints` 被无条件替换。旧指纹与现指纹是否一致**从不核对**，差异也**从不报告**。
"程序文件指纹逐次核对"（`lib/engine.js:38` 注释里明确宣称的设计目标）在重登记这条路径上**被完全绕过** —— 只要能让执行端重新登记一次，任何被替换过的执行端都会被认为是"合法的"。

**建议**：`register()` 检测到 `state.endpoints[e.id]` 已存在且指纹不同时，**失败并报告差异**（或进入上面缺陷 1 的"待确认"状态），而不是覆盖。

## 缺陷 3 ★★ 没有"单独结束某个任务"的能力（用户提的）

### 现象

用户原话：「**没有手动结束任务的按钮了**」。

界面上只有一个「取消任务」按钮，而它是**会话级全量取消**：一按下去，**所有**未完成任务 + 派发全部停止。

### 代码

```js
// lib/engine.js:272-273   control 的粒度是 session
async control(actor,action){
  const s=this.session(actor);
  requireValue(['pause','resume','cancel'].includes(action),'操作无效');
  if(action==='resume'){ ... }
  else{ s.paused=true;
        for(const t of s.tasks){                       // ← 遍历本会话所有任务
          if(!unfinished.has(t.status)&&t.status!=='paused')continue;
          if(action==='cancel')t.cancelRequested=true;
          t.recovery_from=t.status;
          const live=this.live.get(t.runId);
          if(live){t.status='stopping';live.controller.abort();}
          else t.status=action==='cancel'?'cancelled':'paused';
        }
        this.event(s,action,action==='pause'?'暂停派发，正在停止受管工作':'取消本会话工作');  // ← "取消本会话工作"
        ... }
```

### 期望的修复（建议）

1. `coordinator_control` 的 `cancel` 支持可选 `id`（任务编号）：
   - 给了 `id` → 只取消该任务（若它在运行，则 abort 它对应的 `live.controller`）；
   - 未给 `id` → 保持现在的会话级语义（向后兼容）。
2. `engine.control(actor, action, id)` 相应分流，**只遍历目标任务**。
3. 界面：在**每个任务行**上加"结束此任务"按钮（仅对未完成任务显示），并**加二次确认**（因为不可撤销）。
4. 注意与 `lib/engine.js:273` 里 `settling` 等待逻辑的配合：单任务取消时只等该任务的 promise，不要等全会话。

补充：`unfinished` 集合定义在 `lib/engine.js:36`，改 cancel 时需沿用同一判据：

```js
const unfinished=new Set(['running','stopping','awaiting_review','queued','blocked']);
```

（注意 `blocked` 也在内 —— 单任务取消要能结束"需要处理"态的任务，这类任务当前只能靠会话级 pause/cancel 或 `recover` 处理。）
