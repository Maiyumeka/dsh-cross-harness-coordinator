## 六、需要查清的问题（我没有区分开，请协助定位）

### Q1 `native.js` 的 `requestApproval` 到底被调用了没？

```js
// lib/native.js:11-12
const requestApproval=async m=>{
 const p=m.params||{},audit={requestId:m.id,method:m.method,itemId:p.itemId||null,decision:'cancel',reason:''};
 approvals.push(audit);if(approvals.length>64)approvals.shift();
```

`approvals.push()` 在函数**第一行**。既然最终 `approvals: []` 为空，则要么：

- **(a)** `requestApproval` 从未被调用 —— 说明请求在更早的地方就被拒了（例如 `native.js:14` 的 `if(!scoped)` 分支，但那也会返回 cancel 而不 push）；
- **(b)** 被调用了，但整个 `approvals` 数组在异常路径上丢失/未进最终 receipt。

**请确认 `approvals` 是何时被写入 `connectionReceipt` / `native` 的**，以及异常退出时是否会丢。

### Q2 为什么没有任何拒绝原因留下？

我查过：

```
· E:\DFY\history\profiles\desktop\.plugin-manager\logs\**   → 无"审批路径超出任务工作区"等字样
· E:\DFY\history\storages\cross-harness-coordinator\**       → 无
```

`codex-approval.js` 里的 `check()` 抛出的具体原因（例如 `审批路径超出任务工作区`、`缺少完整命令`、`请求涉及额外权限或网络/目录授权`）**都没有落盘**，也没有进 `audit.reason`（因为数组是空的）。

**建议**：审批被拒时的原始异常必须进 `audit.reason` **并落日志**，否则每次失败都只能靠手工复现。

### Q3 怀疑点：搬文件命令里的源路径在工作区外

imagegen 技能规定图片默认落在 `$CODEX_HOME/generated_images/<threadId>/`，**然后必须复制到项目工作区**（技能原文：*"Never leave a project-referenced asset only at the default `$CODEX_HOME/*` path."*）。

而 `codex-approval.js` 的 `workspacePath()` 只允许工作区内路径：

```js
const root=fs.realpathSync(cwd),target=path.resolve(root,value),relative=path.relative(root,target);
check(!relative.startsWith('..')&&!path.isAbsolute(relative),'审批路径超出任务工作区');
```

`C:\Users\Maiyumeka\.codex\…` 与 `E:\DFY` 是不同卷 → `path.relative` 必然返回 `..` 开头 → **必然抛错**。

**但注意**：我的手工对照 C 也走同一条命令、同一工作区，却成功了 —— 因为**手工时我直接 `accept`，绕过了 `codexApproval()` 的路径校验**（我的探针不调用这个函数）。

**所以这条推断需要验证**：请检查 `engine.js:252` 的 `requestApproval(record,proposal)` 在 `codexApproval()` 抛错时的行为 —— 是**返回 cancel**（→ codex 收到 cancel，回合中止），还是**抛出异常导致整条路径静默失败**（→ 审批数组为空、无日志）。后者能同时解释 Q1 与 Q2。

### Q4 沙箱策略与"完全权限"的错配（设计层面）

- 澜（DSH）侧是完全权限；
- 但协调器启动 codex 时 `sandbox_policy` 落到 `read-only`、`approval_policy=on-request`；
- 用户侧不会看到任何审批窗口（预期：由程序代答）。

**请确认派发时是否应显式带上写权限**，例如在 `argv` 里加：

```
-c sandbox_policy="workspace-write"      （实测 app-server 接受该键，未报未识别）
```

注意：我实测 `-c sandbox_policy="workspace-write"` 与不加参数在**简单写文件**场景下都成功，所以它**不是**当前失败的直接原因；但它能减少"需要审批"的面，从而降低对审批代答链路的依赖。

### 4. 由此形成的推断（标明为推断）

```
回合在【图片生成完成之后、发出下一条命令之前】被终止，
且没有在 codex 侧留下拒绝记录、没有在协调器侧留下审批记录。

因此最可能的方向不是"审批被拒"，而是：
  · 协调器侧在收到某个通知/请求时抛了异常（例如 codexApproval() 的 check() 失败），
    该异常发生在能写下 audit 之前，于是 approvals 为空、且异常文本未落日志；或
  · 回合被 deadline/abort 提前终止（但失败信息是"完成事件前退出"而非"超时"，与此不完全吻合）

**需要插件侧补的观测点（这是本工单最主要的诉求）**：
  1. native.js 的 onRequest 进入时先落一条日志（方法名 + itemId + turnId），
     这样能立刻区分"请求没来"与"请求来了但被拒"；
  2. engine.js:252 的 requestApproval 每个 requireValue 失败点单独落日志；
  3. codexApproval() 抛出的原始 message 必须进 audit.reason 并落盘。
```
