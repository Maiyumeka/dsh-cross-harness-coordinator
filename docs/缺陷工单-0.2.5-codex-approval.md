## 已实测的完整因果链

### ① 协议本身完全可用（我手工验证）

用登记的同一入口 `codex.exe app-server --listen stdio://`（`CODEX_HOME=C:\Users\Maiyumeka\.codex`）逐条发 JSON-RPC：

```
initialize   → ✅ {"userAgent":"probe/0.160.0 (Windows 10.0.26200; x86_64)…","codexHome":"C:\\Users\\Maiyumeka\\.codex","platformFamily":"windows"}
model/list   → ✅ 返回完整模型目录（gpt-6.1-sol / gpt-6-astra / …）
thread/start → ✅ 成功创建线程（cwd=E:\DFY\video\art）
turn/start   → ✅ 返回 turn.id，status=inProgress
```

**结论：握手、模型发现、线程创建、turn 启动，全部正常。**

### ② 卡点在"执行命令需要审批"

`turn/start` 之后收到的通知（去重）：

```
remoteControl/status/changed, account/updated, thread/started,
mcpServer/startupStatus/updated, thread/status/changed, turn/started,
item/started, item/completed, item/agentMessage/delta,
item/commandExecution/requestApproval        ← ★ 关键
```

一等模型要执行命令，服务端就发 `item/commandExecution/requestApproval`，**等客户端批准**。

### ③ 协调器一律回 cancel → turn 无法完成 → 进程退出

```js
// lib/native.js:6-10
const rpc=await openRpc(host,r,{argv:[...],onRequest:m=>{
  if(['item/commandExecution/requestApproval','item/fileChange/requestApproval'].includes(m.method))
     return {result:{decision:'cancel'}};            // ← 一律取消
  if(m.method==='item/permissions/requestApproval')return {result:{permissions:{},scope:'turn'}};
  if(m.method==='mcpServer/elicitation/request')return {result:{action:'cancel',content:null}};
  return {error:{code:-32601,message:'需要用户交互；协调器不自动授予额外权限'}};
```

被 cancel 后模型写不了文件，turn 无法 completed：

```js
// lib/native.js:24
rpc.h.done.then(()=>reject(Error('Codex在完成事件前退出')),reject);
```

### ④ 对照实验：审批回 `accept` 就能正常完成

我用同一入口、同一提示词（"在工作目录创建文件 codex-probe.txt，内容写 OK"），把审批响应改成 `accept`：

```
审批请求 1 次 | turn/completed = true | 文件生成 = true (2 B) | 内容 = "OK"   ✅
```

**证明：不需要任何放权参数，默认配置 + 一次批准即可完成文件交付。**

### ⑤ 顺带确认的正确响应格式

我第一次尝试用 `{decision:'approved'}`，服务端报：

```
failed to deserialize CommandExecutionRequestApprovalResponse:
unknown variant `approved`, expected one of `accept`, `acceptForSession`, …
```

**正确枚举是 `accept` / `acceptForSession`（不是 `approved`，也不是 `cancel`）。**

### ⑥ `-a never` 在 app-server 上不可用

`codex app-server` 不接受顶层/exec 的 `-a` / `-s` 参数：

```
codex.exe app-server --listen stdio:// -a never
  → stderr: For more information, try '--help'.        （参数不被识别）
```

`app-server --help` 只提供 `-c, --config <key=value>` 做配置覆盖。**所以"靠加参数绕开审批"这条路对 app-server 不成立。**

## 缺陷 1（主）：审批一律 cancel，使 Codex App Server 端无法完成任何需要执行命令的任务

**影响**：该端只能做纯文本回合。任何要落盘的任务（写文件、跑命令）必然失败，且失败信息只有一句"Codex在完成事件前退出"，无法自证原因。

**建议修复方向**（三选一，按安全性排序）：

1. **在非交互派发时回 `accept`（最小改动，推荐）**
   - 派发一个任务本身就是用户的授权行为；协调器可以用 `accept` 响应工作区内的执行/改文件请求。
   - 沙箱策略仍由 Codex 自身决定，**不需要任何危险参数**。
   - 若要更保守，可用 `acceptForSession`，把批准限制在当前会话内。
2. **可配置**：给 codex 协议端加一个显式配置项（例如 `mcp`/`cli` 之外的 `codex.approvals: 'accept' | 'cancel'`），默认保守、由登记会话按需开启，并在回执里如实标注当前策略。
3. **保持 cancel，但要让失败可自查**：至少把"审批被协调器拒绝"这个原因明确写进 `error`，而不是只报"完成事件前退出"。

**不要**改成 `--dangerously-bypass-approvals-and-sandbox`：实测证明完成文件交付**不需要**它，而那会带来无沙箱的任意命令执行能力。

## 缺陷 2（次）：进程提前退出时，原始输出与 stderr 全部丢失

```js
// lib/native.js:22-27
const terminal=completed.get(turnId)||await new Promise((resolve,reject)=>{
 waiter=resolve;timer=setTimeout(()=>reject(Error('Codex任务超时')),r.task.timeoutMs);
 const abort=()=>reject(r.signal.reason||Error('任务取消'));r.signal.addEventListener('abort',abort,{once:true});
 rpc.h.done.then(()=>reject(Error('Codex在完成事件前退出')),reject);
```

`h.done` 提前触发时，`reject(Error('Codex在完成事件前退出'))` **不带任何 output / stderr**，而正常返回路径（line 28）才附带 `output` 与 `rpc.stderr`。于是：

```
result: null
error : "Codex在完成事件前退出"      ← 排查时没有任何线索
```

**建议**：该 reject 至少携带已累积的 `output`、`rpc.stderr`、`phase`，以及最后收到的通知方法名。本次若早有这样的信息，根因（审批被拒）在第一次失败时就能看出，不必手工复现。
