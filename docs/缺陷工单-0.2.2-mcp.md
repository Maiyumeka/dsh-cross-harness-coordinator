## 实测证据（全部由本机复现，非推测）

### 1. OpenSquilla 网关的原始协议行为

直接以 `mcp-server run` 起 stdio，逐条发 JSON-RPC：

| 请求 | 响应 |
|---|---|
| `server/discover` `{}` | `{"code":-32601,"message":"Method not found","data":"server/discover"}` |
| `initialize` `{protocolVersion:'2025-11-25', capabilities:{roots:{listChanged:false}}, clientInfo:{name:'dsh-cross-harness-coordinator',version:'0.2.2'}}` | ✅ `{protocolVersion:'2025-11-25', serverInfo:{name:'OpenSquilla',...}, capabilities:{tools:{listChanged:false},...}}` |
| `initialize` 最小 params | ✅ `protocolVersion=2025-11-25` |
| `initialize` `{protocolVersion:'2026-07-28'}` | ✅ 成功（服务端回 `2025-11-25`） |
| `initialize` 只有 `protocolVersion`（缺 capabilities/clientInfo） | ❌ `{"code":-32602,"message":"Invalid request parameters"}` |

**要点：网关认 legacy `initialize`（任何版本号都接受），但不认 `server/discover`（-32601）。**

### 2. 协调器的错误状态不可直连复现

用与协调器**完全相同**的 params 直连 `initialize`，**成功**。
而协调器经同一入口收到 `-32022 connection is serving the 2026-07-28 protocol`。

→ **强烈指向服务端有连接级状态**：协调器在 `era:auto` 下先发了 `server/discover`，把该连接推进到现代模式，此后再发 legacy `initialize` 就被拒；直连不先发 discover，所以成功。

（这一点我无法在不改动服务端的前提下 100% 证实，故如实标注为"最可能解释"，但两条报错路径的差异是实测的。）

## 缺陷分析

### A. 降级判据太窄（主因）

`server/discover` 不可用时，服务端的拒绝形态**不止 -32022 一种**。OpenSquilla 回的是：

```
-32601 "Method not found"        （明确说不认识这个方法）
```

插件只认 `-32022`，于是走 `else` 分支——这一支在 `era:'auto'` 下**理论上会降级**。

但第二次重试返回 `stage:server/discover` + **超时**，说明该路径下 `server/discover` **无人应答**（不是抛 -32022）。此时 `req()` 会以 `Error('MCP连接或调用超时：server/discover')` 拒绝，这个错误**既没有 `rpcError.code` 也没有 `rpcError.data`**：

- `error.rpcError?.code===-32022` → false
- 于是走 `else`，`e.mcp.era==='auto'`、未 abort、未 fatal → **应该 `modern=false` 降级**

**但结果仍是 `needs_agent`，且第一次报错显示它确实降级并发了 `initialize`，然后被 -32022 拒。** 两条路径合起来的净效果是：**无论走哪条分支都连不上**。

### B. 现代路径对"未实现 server/discover"的服务无解

即使降级成功，legacy `initialize` 也被服务端以 `-32022 serving the 2026-07-28 protocol` 拒绝——即服务端自称已是 2026-07-28 时代，而现代路径又依赖它没实现的 `server/discover`。

**这是双输**：服务端只认 2026-07-28，却不提供该时代的发现方法；客户端只会用 `server/discover` 进入该时代。

## 期望的修复（建议）

1. **降级判据扩宽**：`server/discover` 的失败应当涵盖
   - `-32601 Method not found`
   - 请求超时（服务端不实现该方法时常常静默）
   - 任意"该方法不可用"形态
   → 只要**尚未取得 `resultType==='complete'` 的 discover 结果**，就应降级 legacy initialize，而不是把它当成致命错误。

2. **区分"现代协商失败"与"连接失败"**：当前 `stage` 会在 `server/discover` 与 `initialize` 之间摇摆，同一次障碍留下两条不同归因的报错，排查时容易误判。建议失败时把**两条路径的原始错误都带上**（例如 `attempts:[{era:'modern',error:...},{era:'legacy',error:...}]`）。

3. **`era:auto` 的判定顺序可选反转**（或加配置）：对明确声明了 legacy 能力（能正确回 `initialize` + `protocolVersion`）的服务端，先用 legacy 试一次成本极低；只在 legacy 被明确要求现代协议时才进 `server/discover`。当前顺序（先 discover）会在**有状态的服务端**上污染连接，如本次现象所示。

4. **`server/discover` 的请求超时应短且可区分**：`lib/mcp.js:104` 里 discover 已有 1500ms 上限，但报错文案与普通超时混同，无法区分"方法不存在"与"服务端卡住"。
