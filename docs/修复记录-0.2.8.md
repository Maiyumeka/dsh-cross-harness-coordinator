# 0.2.8：计划参数拒绝的定位与原子提交

对应[0.2.7 coordinator_plan 工单](缺陷工单-0.2.7-coordinator-plan-rejected.md)。

## 已复现的原因

工单的直接调用示例有任务 title；后来失败的最短JSON没有 tasks[0].title，两份数据并不相同。用工单短示例（任务JSON为247个UTF-8字节）和正式桌面app.asar内的DSH 0.2.0-rc.2 schema/defineTool代码，在独立目录复现：缺少任务title报“字段需要有效文字”；补上title后越过文字校验，直到测试环境中未登记端点的可见性检查。

因此该样例的报错来自插件engine.text，而非宿主隐含字符串长度限制，也不是Codex入口更新。宿主defineTool的string类型校验未声明或实现maxLength，错误是INVALID_ARGS / invalid arguments及字段路径；其schema代码无“字段需要有效文字”文案。实际0.2.0-rc.2旧string参数测试也接受了含32000字符prompt的JSON字符串；插件自己的prompt限制仍为16000个UTF-16码元。以上不推断网络传输或宿主其它层没有大小限制。

没有取读现场聊天历史，故不能把所有历史失败一概归为缺标题；新版错误应提供逐次判断所需的证据。

## 修改

- 文本、编号和数组校验明确字段路径，如tasks[0].title、tasks[1].prompt、tasks[0].criteria[0]，同时给出收到的类型、长度、UTF-8字节（字符串）与限制值。长度限制沿用JavaScript字符串的UTF-16码元，不能把UTF-8字节当字符限制。
- error.validation只保存元数据：layer、field、received、expected及maxLength/minItems/maxItems，不回显任务正文或原始JSON。区分tool/schema、tool/json、engine。JSON解析错误不暴露JSON.parse带出的原文片段。
- 对真正的宿主INVALID_ARGS保留其错误类、代码和严格schema，只补充诊断；没有把不合法参数当有效参数执行。UI RPC错误也提供validation details。
- coordinator_plan.tasks的公开schema接受结构化array或原JSON字符串，两种形式进入同一任务校验；每项必填id/title/prompt/endpoint/outputs/criteria/reason，dependencies可省略，默认[]。计划title与每项任务title分别必填，不自动编造标题。数组items只做JSON完整性检查，嵌套字段及长度统一由引擎验证，避免两种形式报错不一致。
- 工具描述和系统指导明确标题要求、可选字段及失败后按字段修正，不反复重发原参数或修改无关Harness配置。
- 计划总标题先验证，再替换任务或归档旧计划。原先“s.tasks=normalized; s.title=text(title)”可能在总标题无效时先改掉内存任务列表，现已修正。拒绝的计划不覆盖既有任务、历史或派发任务。
