# 0.2.6：Codex 单次操作审批和异常退出诊断

对应 [Codex approval 工单](缺陷工单-0.2.5-codex-approval.md)。此前命令/改文件请求固定返回 cancel，又在提前退出时抛出无输出的错误，导致需要审批的文件任务受阻、难以判断失败原因。不能把这一失败认定为模型绘图能力不足，也不能据此断言所有文件任务都一定需要审批。

## 审批闭环

普通命令和文件补丁现在进入原任务会话的待处理审批。界面显示等待批准，并提供完整命令、工作目录或实际文件差异。用户核对后可“批准这一次”；Agent 使用 coordinator_control action=approval，由 DSH 现有 approval.request 在原会话的真实工具回合中审查，只有 allowed-once 才回复 accept。DSH 的拒绝、never 策略或缺少答复渠道都不构成批准。

操作标识和版本绑定 task/runId/revision/threadId/turnId/itemId，只处理仍活着的原任务。批准不会重派、重开线程或重复模型请求。accept 是单次批准；acceptForSession 范围更大，不是更保守的选择，未采用。命令解析提示只供展示，不能用 cwd 或 commandActions 自动判断全部副作用均获授权。

网络、额外目录/权限授权、grantRoot、elicitation 和未知交互仍明确拒绝，不能混作普通写文件操作。缺少完整命令/补丁、原路径或移动目标路径/链接越界、旧版本、跨会话、过期、重复答复均不批准；取消、暂停、回合结束、任务结束或重启撤回待处理审批。答复前再次检查路径/链接边界和操作内容是否变化。临时 one-shot 批准不修改 config.toml、沙箱配置、账户或系统权限。

stdio 和 Codex WebSocket 都经过同一审批流程；WebSocket 的审批在受管工作进程与宿主之间往返，保留会话沙箱。RPC 反向请求支持异步答复，审批等待期间继续接收通知。登记检查不进入审批、不创建任务回合；Codex 握手和模型目录仍不证明模型访问或绘图可用。

协议核对使用本机 Codex CLI 0.160.0 的 generate-json-schema，以及 [官方 App Server 审批文档](https://learn.chatgpt.com/docs/app-server#approvals)。没有使用不存在的 approved 枚举，没有添加 -a/-s、危险跳过参数或修改既有配置。

## 失败诊断

Codex 完成事件前退出、超时或审批拒绝返回 ok=false，保存之前的文字输出和 stderr、命令输出、阶段/最后通知、退出码、审批决策与原因；失败结果进入协调器 result，缺失产物不会放行。常见凭据形态隐藏，记录长度受限。取消后的已收集诊断也保留，但任务仍为 cancelled/paused。

## 回归和验证范围

新 codex-approval.mjs 用独立协议进程模拟实际服务端审批，批准前不写文件，单次 accept 后在同一回合落盘 OK（2字节）；覆盖命令/文件、早于 turn/start 回复的请求、第二个请求仍需审批、跨线程/回合拒绝、额外权限拒绝、DSH 允许/拒绝/不可用、取消后迟到批准、重启不复活，以及 stdio/WebSocket。提前退出保留原输出和 stderr 的断言不依赖真实模型。

界面回归验证具体操作可见、“返回”不投票、“批准这一次”只解决目标审批；原单任务结束、历史产物、重确认及窄屏仍检查。完整核心套件加入这一套件，共 13 项；重复日志和发布哈希见 dist/验收记录-0.2.6.json。

最终验收：完整套件连续两轮通过（每轮13项，共26/26），Edge界面回归通过。发布包38个文件，逐文件源码/清单哈希一致。命令/文件审批、拒绝后原输出和stderr、原会话授权边界、WebSocket转接，以及原路径/移动目标/链接检查均通过无模型协议夹具验证；这不替代真实DSH中的模型任务或媒体验收。

本轮不提交真实模型任务，不自动重做 art-probe，不触碰正式协调器状态或 Codex 配置。真实图片生成与视觉审查尚未验收。生成独立 0.2.6 包，正式 DSH 安装/激活与真实任务批准仍由原 DSH 会话按 AGENT_INSTALL.md 进行。
