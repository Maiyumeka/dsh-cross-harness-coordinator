# 0.2.1 修复记录

对应 [0.2.0 缺陷工单](缺陷工单-0.2.0.md)。本版修复工单里的三项问题；原工单保留，方便对照。

## 指纹失效后的恢复

原实现发现启动文件变化后，只有“重新确认接入”的错误文字，缺少实际确认动作；重新登记同一端点又会直接重算并覆盖基线。0.2.1 保留拦截，并提供明确恢复路径：

1. `coordinator_control action=reconfirm id=执行端编号` 只查看差异，不更新基线、不启动进程。
2. 返回逐文件旧/新 SHA256、修改时间，以及绑定端点、调用定义和当前字节的 `confirmationVersion`。
3. Agent 核对实际入口后，携带 `confirmation_version` 和 `note` 再次执行 reconfirm。设置页对应“查看变化并重新确认” → 查看差异 → “确认变化并验证”。
4. 明确确认才写入新基线并保存旧基线、确认者、依据和时间，随后插件执行无任务连接验证。查看后文件或定义再次变化时，旧确认被拒绝。验证期间再次变化仍会拦截。

已有 passed 任务不阻止对同一调用定义重新确认指纹，且任务、产物、历史审查记录保持原状；不会自动恢复或重派任务。其他会话、正在运行或检查中的端点不能被重新确认。更改调用定义仍保留任务引用保护。

重登记检测到指纹差异时会拒绝，不能借此静默刷新基线。connect 修正入口涉及新文件时，返回候选定义与差异；确认时须携带同一个 definition。API 与界面均保留这一门槛。缺失或不可读取的启动程序不能被确认成可用。

指纹失败的 stage 改为 `fingerprint`。旧版缓存中因指纹错误误标的 `launch` 会在升级加载时归入 fingerprint；实际差异仍由当前文件重新计算，不把缓存错误当成新基线。

## 版本证据

当前工单所指磁盘 CLI 的 package 版本为 0.1.2-rc.1，登记记录申报 0.2.0-rc.2，旧/新文件哈希不同。登记旧哈希 1a03dee1…与桌面 app.asar 内置 CLI 的完整哈希一致；当前磁盘入口为 dc23f6c5…。文件修改时间本身不能证明文件从未被替换或从归档恢复；这里能够确认的是当前入口和已登记基线不一致，不能仅据此断言初始登记就是错误的。

0.2.1 将 `reportedVersion` 与实测版本分开。存在安全的 probe_args 时，插件通过同一个 command 和启动脚本运行 --version/-V，前后核对指纹。成功后 versionSource=entry_probe，显示“实测版本”；不满足同入口无任务规则或无法提取确定版本时，保持“申报版本”，不假报实测。协议 agentInfo/serverInfo 的组件版本单独保存，不把组件版本或桌面安装版本当成 CLI 版本。

## 单任务结束

`coordinator_control action=cancel id=任务编号` 只取消指定任务；未传 id 时，保持会话级取消语义。单项操作不会把会话切成暂停状态，也不会等待或中止其他运行任务。仅允许未完成及 paused 任务；passed、failed、unverified、cancelled 任务不重复取消。

界面每个未完成任务显示“结束此任务”，查看确认后才提交该 id；“返回”不会提交。会话级按钮改为“结束全部任务”，也须确认。已有文件保留，依赖于已取消任务的工作不会因此获得通过资格。运行或返工停止中的任务在结束时不会被旧的 invalidated 标记重新排队。

## 验证

- defects-0.2.1.mjs：真实文件替换、重登记拒绝、确认令牌过期、握手期间竞态、三个历史 passed 任务保留、同入口版本、单项取消各状态、工具和 RPC。
- defects-ui.mjs：实际浏览器验证每行按钮、确认/返回、只传目标 id、差异查看、重新验证、版本展示、全部结束及窄屏布局。
- 默认核心测试加入缺陷回归；UI 测试单独执行，避免将缺浏览器环境算成通过。

在最终中文项目目录复跑还复现了 Python 工作进程沿用 Windows 默认编码的问题：UTF-8 请求中的中文路径会被误读。本版同时将 Python 标准输入/输出/错误通信固定为 UTF-8，mainstream 测试改用中文工作目录，验证 Node 与 Python 两侧路径一致。

这些测试使用隔离进程及假协议入口，不调用付费模型，也不替用户接受正式执行端的新指纹。正式端点的恢复须通过以上明确确认路径。安装检查继续保留 a9adf3a 的 ASAR 取证修复。
