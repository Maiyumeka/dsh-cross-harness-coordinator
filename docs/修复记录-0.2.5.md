# 0.2.5：原失败阶段保持稳定，预算测试使用可控时间

对应 [0.2.4 flaky 工单](缺陷工单-0.2.4-flaky.md)。0.2.4 在一次完整套件中通过，不代表稳定；工单随后记录六次套件运行中一次 initialize/cleanup 阶段不一致。本轮保留严格断言，并修复了实际错误覆盖。

## 确定性复现与实现修正

initialize 静默时，请求计时器与总预算计时器可以落在同一截止点。如果请求计时器先拒绝请求，catch 已经记录 initialize；随后的 finally 清理结束看到预算耗尽，而总计时器又已被清除、fatal 为空，就创建 cleanup 错误覆盖原错误。不是网关或宿主报错，也不是只能放宽测试断言的问题。

先引入局部可控时钟、保持旧错误处理逻辑，显式先执行 initialize 的超时回调，稳定复现实际 cleanup、期望 initialize。修正后，原失败在 catch 中固定：错误消息/代码、protocolStage、failedPhase、failure 和协商尝试均保留；最终清理只补充 cleanupMs、cleanupFailure、cleanupDeadlineExceeded 和最终取消状态。清理超期、清理自身失败或清理期间取消，不覆盖先前的握手失败。

若握手/调用原本成功而最终清理首次失败，仍报告 cleanup 并拒绝 ready。用户取消和总期限不被撤销，不延长预算、不增开连接、不重放 tools/call。进程仍由原宿主管理启动与停止。

同时，stopConnection 在进程先结束时清除 200ms 的等待定时器，避免留下无用回调。设置中的连接记录显示原失败阶段及补充清理信息，Agent 也可从完整回执诊断原失败和最终清理状态。

## 测试修正

time.js 提供默认真实时钟，作为宿主内部依赖；测试启动器才传入独立 FakeClock。登记定义和 Agent 请求无法选择时钟。MCP、共同预算与同入口版本预检使用同一时钟；其余协议行为保持原有逻辑。测试不替换全局 Date/setTimeout，因此同进程 import() 的前后套件不受虚拟时间影响。

mcp-budget.mjs 去掉真实 150/250/300/650ms 窗口和墙钟上限断言，按虚拟时间推进启动、版本预检、超时和清理。保留 protocolStage=initialize 的严格判断，没有把 cleanup 加进允许集合。

100 次固定组合覆盖请求超时优先/总超时优先、截止点立即执行/延迟 50ms 执行；两个路径都保持 initialize，也验证原错误代码、双路径协商和总超时来源。另测已有 RPC 错误后的清理超期、清理自身失败、清理期间取消，以及操作成功后才出现清理失败。每个场景结束都检查虚拟定时器无泄漏；模型工具调用为零。

完整核心套件仍保留同进程顺序 import()，没有通过更换跑测方式隐藏问题。最终重复运行结果和发布哈希见 dist/验收记录-0.2.5.json。

本轮验收：完整套件连续 **6/6 轮通过**，每轮 12 项，共 **72/72 项**。每轮包含 100 次固定超时顺序检查。Edge 界面测试通过，原失败阶段可见，单任务结束、历史产物和窄屏检查保持通过。新版包包含 36 个文件，源码/安装包/发布清单逐文件哈希一致。

真实登记网关的独立无任务复测也通过：auto 返回 2026-07-28、6 个工具，约 3.36 秒；legacy 返回 2025-11-25、6 个工具，约 3.20 秒。它使用测试启动器，不是正式 DSH 宿主验收；没有 tools/call，也没有修改正式协调器状态。

可复核的重复入口为 node test/repeat-core.mjs，默认重复六轮；每轮仍执行原 test/run.mjs，日志和 JSON 摘要保存到 test-data/repeat-core-*。失败即停止并返回非零，不把未完成或失败标为通过。

## 验证边界

本轮只生成源码和新版本包，不安装 0.2.4 或自动替换正式 DSH，不修改正式协调器状态、登记入口、邀请或任务。此前 0.2.4 包保留，本轮使用独立名称的 0.2.5；按 AGENT_INSTALL.md 验证后再由正式 DSH 完成安装与运行验收。
